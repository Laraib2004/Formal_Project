# How the Recipe Compiler Works

*Implementation notes — Formal Languages and Compilers project*

`DOCUMENTATION.md` describes the **language**: what you are allowed to write and
what the grammar accepts. This file describes the **compiler**: the data
structures, how a source file travels through them, and exactly how scoping is
implemented. Read this one if you are modifying the code.

---

## 1. The shape of the compiler

Everything lives in two source files. There is no separate symbol-table or
AST module, which keeps the project small enough to read in one sitting.

```
recipe.txt
    │
    │  recipe.l  (flex)          105 lines
    ▼
  tokens  ──  each carries its value in yylval
    │
    │  parser.y  (bison, grammar section)      865 lines total
    ▼
   AST    ──  one node per language construct
    │
    │  parser.y  (analyze_* functions)
    ▼
  report  ──  symbol table, types, constant values, warnings
    │
    ▼
 exit 0 or 1
```

The three stages are strictly separated, and that separation is the main design
decision in the project:

| Stage | Does | Does **not** do |
|---|---|---|
| Lexer | text → tokens, `atoi`/`atof` conversion | no syntax or type rules |
| Grammar actions | build AST nodes | **no semantic checks at all** |
| Tree walk | every semantic rule, exactly once | never re-parses text |

Because the grammar actions are a pure translation scheme, each production does
nothing but assemble a node and hand it up as a synthesized attribute. All the
judgement happens later, in one pass over the finished tree.

### Why this matters

Two consequences are worth knowing before you change anything:

- **Numbers become values once.** `atoi`/`atof` run in the lexer (`recipe.l:76`,
  `recipe.l:81`) and the result is stored in the AST as a real `long`/`double`.
  Nothing ever converts a number back to a string.
- **Operators are stored as codes, not text.** `op_kind` (`parser.y:51`) holds
  `OP_ADD`, `OP_MUL` and so on, so the analyser switches on an enum instead of
  calling `strcmp(op, "+")`. The `"+"` text exists only in `op_symbol()`
  (`parser.y:235`), used for printing.

## 2. Files

| File | Role |
|---|---|
| `recipe.l` | Lexer: token regexes, attribute values, comments, line counting |
| `parser.y` | Grammar, AST, symbol table, semantic analysis, `main` |
| `makefile` | Build, `run`, `test`, `clean` |
| `run_tests.sh` | Runs every example and checks its exit status |
| `DOCUMENTATION.md` | Language reference and EBNF grammar |
| `INTERNALS.md` | This file |

Generated by the build, never edited by hand and never committed:
`lex.yy.c`, `parser.tab.c`, `parser.tab.h`, `parser.output`, `compiler`.

`parser.output` is the LALR state-machine dump that `bison -v` produces. It is
the file to read when you add a production and bison reports a conflict.

## 3. Stage 1 — Lexical analysis (`recipe.l`)

Flex options are set at the top of the file:

- `%option yylineno` — flex maintains the current line number, which is how
  every diagnostic in the compiler gets its line. Nothing counts newlines by hand.
- `%option noyywrap` — one input file only, so `libfl` is not needed and the
  link step stays `gcc` with no extra library.
- `%option nounput noinput` — suppresses two generated functions the project
  never calls, which keeps `-Wall` silent.

Rule order in the file is deliberate:

1. Keywords come before the identifier rule. Flex prefers the **longest** match
   and, on a tie, the **earliest rule**, so `cook` is the keyword `COOK` and not
   an identifier.
2. Two-character operators (`==`, `!=`, `&&`) come before the one-character ones,
   so `==` never lexes as two `=` tokens.
3. The float rule `[0-9]+"."[0-9]+` requires digits on both sides of the dot, so
   it can never steal a plain integer such as `5`.

Tokens that carry information put it in `yylval`: `int_val` for integers,
`double_val` for floats, `string_val` (a `strdup`) for identifiers and strings.

Trivia — `//` comments and whitespace — is matched and discarded. The last rule,
`.`, catches any character the language does not define and prints a lexical
error and increments `lex_errors`, which `main` checks — a stray character fails
the build even when the parser could carry on without it.

## 4. Stage 2 — Parsing and the AST (`parser.y`)

### Node layout

Every construct is one `ast_node` (`parser.y:56`):

```c
typedef struct ast_node {
    node_kind kind;
    op_kind   op;          /* for NODE_BINOP / NODE_RELOP */
    char     *sval;        /* identifier / string / unit text */
    long      ival;        /* NODE_INT value */
    double    fval;        /* NODE_FLOAT value */
    int       line;        /* source line, for diagnostics */
    struct ast_node *child;
    struct ast_node *sibling;
} ast_node;
```

The tree uses the **child/sibling** representation rather than a fixed array of
children: `child` is the first subordinate node, and `sibling` chains the rest at
the same level. This is why a node needs no child count and why statement lists
of any length cost nothing extra.

So `boil pasta in pot 5 min` becomes one `NODE_BOIL` whose children are a chain
of four:

```
NODE_BOIL
  └─ child: ID 'pasta' ─sibling→ ID 'pot' ─sibling→ INT 5 ─sibling→ UNIT 'min'
```

The analyser reads those positionally: `n->child` is the ingredient,
`n->child->sibling` the container, and so on.

`mk()` (`parser.y:69`) stamps `n->line = yylineno` on every node as it is built.
That single assignment is the reason error messages can name a line long after
parsing has finished — the lexer's position is captured at construction time and
travels with the node.

### Operator precedence

Precedence is declared, not encoded in the grammar shape:

```
%left ADD_OP SUB_OP
%left MUL_OP DIV_OP
```

Later declarations bind tighter, so `*` and `/` outrank `+` and `-`. The
`expression → term → factor` chain gives the same result structurally, and
`factor` admits `( expression )` for explicit grouping. This is what makes
`2 + 3 * 4` evaluate to 14 while `(2 + 3) * 4` gives 20.

The grammar is LALR(1) and builds with **no shift/reduce or reduce/reduce
conflicts**.

## 5. Stage 3 — Semantic analysis

One recursive walk (`analyze_program` → `analyze_recipe` → `analyze_step` →
`analyze_stmt`) performs four jobs simultaneously: symbol-table management,
type checking, constant folding, and unused-symbol detection. Nothing is done
twice and there is no second pass.

### The symbol table

```c
typedef struct symbol {
    char     *name;
    sym_kind  kind;        /* SYM_TOOL | SYM_INGREDIENT | SYM_VARIABLE */
    data_type dtype;       /* for variables */
    int       decl_line;
    int       used;
    int       has_value;   /* constant folding succeeded */
    long      ival;
    double    fval;
    char     *sval;
    struct symbol *next;
} symbol;
```

Symbols form a singly linked list per scope, and scopes form a stack
(`parser.y:118`):

```c
typedef struct scope {
    symbol *symbols;
    struct scope *parent;
} scope;
```

Insertion is at the head of the list, so lookup within a scope finds the most
recent declaration first. There is no hashing — recipes declare few names, and a
list keeps the code short and the iteration order useful for reporting.

Two globals track position in the stack (`parser.y:123`):

- `scope_top` — the innermost open scope
- `recipe_scope` — the scope belonging to the current recipe

## 6. Scoping — the part worth reading twice

### Two kinds of name, two lifetimes

This is the central rule of the implementation, and it is asymmetric on purpose.
`insert()` (`parser.y:209`) chooses the destination scope from the symbol's kind:

```c
scope *target = (kind == SYM_VARIABLE) ? scope_top : recipe_scope;
```

| Declared by | Kind | Lives in | Lifetime |
|---|---|---|---|
| `get X` | tool | `recipe_scope` | the whole recipe |
| `add X to Y` | ingredient | `recipe_scope` | the whole recipe |
| `set X = …` | variable | `scope_top` | the enclosing block only |

The reasoning is domain-driven: a pot you fetched inside an `if` is still a pot
you own afterwards, so tools and ingredients are recipe-wide no matter how deeply
nested the statement that introduced them. A variable is ordinary block-scoped
state and dies with its block.

### Which constructs open a scope

| Construct | New scope? |
|---|---|
| `recipe { }` | yes — pushed in `analyze_recipe` (`parser.y:528`) |
| `step N { }` | **no** |
| `if (…) { }` | yes (`parser.y:483`) |
| `while (…) { }` | yes (`parser.y:483`) |
| `repeat N times { }` | yes (`parser.y:499`) |

**Steps deliberately do not open a scope.** A recipe is a single continuous
procedure, so a variable set in step 1 must still be readable in step 3. Only
control-flow blocks nest.

### Lookup

`lookup()` (`parser.y:193`) walks the stack from the innermost scope outward:

```c
for (scope *s = scope_top; s; s = s->parent)
    for (symbol *e = s->symbols; e; e = e->next)
        if (strcmp(e->name, name) == 0) return e;
```

Because `recipe_scope` is the outermost link in that same chain, one loop finds
both block-local variables and recipe-wide tools. The innermost match wins, which
is what makes shadowing work.

`lookup_in()` (`parser.y:201`) searches a **single** scope. The distinction
between the two functions is exactly the distinction between redeclaration and
shadowing:

- `lookup_in(scope_top, name)` finds something → **error**, the name is already
  declared in *this* block.
- Only `lookup(name)` finds it → **legal shadowing**, the name belongs to an
  enclosing block.

So this is an error (`test_for_scope/scope6fail.txt`):

```
set timer = 5;
set timer = 10;        → variable 'timer' is already declared in this scope
```

while this is allowed, and the inner `t` is a distinct symbol:

```
set t = 1;
if (t < 5) {
    set t = 2;         → shadows the outer t
}
```

### Worked example

`test_for_scope/scope3fail.txt` exercises the rule and the tool/variable
asymmetry at the same time:

```
1  recipe Test_IF_Variable_Isolation {
2      step 1 {
3          set base_temp = 80;
4          if (base_temp == 80) {
5              set cooking_time = 15;
6              get pot;
7          }
8          set final_time = cooking_time;
9      }
10 }
```

What the analyser does, in order:

1. Line 1 — `push_scope()` for the recipe; `recipe_scope` now points at it.
2. Line 3 — `base_temp` goes into `scope_top`, which *is* the recipe scope.
3. Line 4 — condition type-checked, then `push_scope()` for the `if` body.
4. Line 5 — `cooking_time` goes into the new inner scope.
5. Line 6 — `pot` is a tool, so it goes into `recipe_scope`, **skipping** the
   inner scope entirely.
6. Line 7 — `pop_scope()`. The inner scope is reported for unused variables, then
   freed. `cooking_time` no longer exists.
7. Line 8 — `lookup("cooking_time")` fails:
   `SEMANTIC ERROR (line 8): 'cooking_time' is not declared`

`pot` survives step 1 and stays usable in later steps; `cooking_time` does not
outlive line 7. Same block, same nesting, opposite lifetimes — that is the whole
rule in one example.

### Cleanup

`pop_scope()` (`parser.y:183`) does three things in a fixed order: report unused
variables, unlink the scope, then free its symbols. Reporting must happen before
freeing, since the warning needs the symbol's `name` and `decl_line`.

## 7. Type checking and constant folding

Two cooperating functions, deliberately kept apart:

- **`type_of()`** (`parser.y:246`) returns the `data_type` of an expression or
  condition and reports type errors. Comparisons evaluate to `T_BOOL`.
  Note that `if (x)` never reaches this check: the `condition` nonterminal admits
  only comparisons and `&&`, so a bare value in a condition is a *syntax* error.
  The `condition must be a comparison` message at `parser.y:482` is therefore
  defensive — unreachable with the grammar as it stands.
- **`eval()`** (`parser.y:303`) computes the constant value where it can, and
  returns `known = 0` where it cannot.

`compatible()` (`parser.y:226`) decides assignability. It allows any int/float
mix, and treats `T_UNKNOWN` as compatible with everything — that is intentional
error suppression. Once a name is undeclared its type is unknown, and
propagating `T_UNKNOWN` silently stops one mistake from cascading into a dozen
follow-on type errors.

Folding propagates through variables: `eval()` on a `NODE_ID` reads `has_value`
from the symbol, so after `set a = 2 + 3 * 4` the symbol for `a` carries 14, and
`set d = a + b` folds to a number rather than giving up. Division by zero is
caught during folding, in both the integer and float branches, and is reported as
a semantic error instead of trapping at runtime.

Folding stops — correctly — at anything string-typed, and at any name whose value
is not statically known.

## 8. Diagnostics and exit status

Three error channels and one warning channel, each recovering differently:

| Kind | Printed by | Recovery |
|---|---|---|
| Lexical error | the `.` rule in `recipe.l` | skips the character, keeps lexing |
| Syntax error | `yyerror` (`parser.y:590`) | resynchronises on `;` |
| Semantic error | `sem_error` (`parser.y:145`) | continues, so all are reported |
| Warning | `sem_warn` (`parser.y:154`) | never affects exit status |

All three error kinds keep going rather than bailing on the first problem, by
three different mechanisms.

**Lexical errors** are the simplest: the catch-all rule reports the stray
character, bumps `lex_errors`, and lets flex carry on with the next character.
The token stream is simply missing whatever the character would have been.

**Syntax errors** recover through one production (`parser.y:680`):

```
stmt: ...
    | error SEMICOLON { yyerrok; $$ = NULL; }
```

On a malformed statement the parser discards tokens until it reaches a `;`,
`yyerrok` clears the error state, and parsing resumes at the next statement. So
a file with three bad statements reports three errors, not one:

```
SYNTAX ERROR (line 3) near ';': syntax error
SYNTAX ERROR (line 4) near 'to': syntax error
SYNTAX ERROR (line 5) near ';': syntax error
COMPILATION FAILED: 3 syntax error(s).
```

The limit of this scheme is that recovery *needs* a semicolon to find. A
**missing** `;` makes the parser consume forward to the next one, swallowing any
further error in between — which is why two missing semicolons in a row report
only one error.

**Semantic errors** need no such trick: `sem_error` increments a counter and
returns, so one walk reports every semantic problem in the file — `type_test.txt`
deliberately produces four.

`main` (`parser.y:833`) decides the exit status:

```
syntax errors > 0   → print the count, exit 1   (AST is not walked)
lexical errors > 0  → print the count, exit 1   (AST is not walked)
semantic errors > 0 → exit 1
otherwise           → exit 0
```

Syntax errors are checked before lexical ones because a stray character usually
breaks the parse too, and in that case the syntax message is the more useful of
the two. Either way the exit status is `1` and the AST is never walked, so you
never see type errors from a file that did not parse.

## 9. Known limitations

- **No code generation.** The project ends at semantic analysis; there is no
  intermediate representation or back end.
- **`float` and `string` variables are accepted but barely exercised** by the
  test suite, which is mostly integer arithmetic and scoping.
- **The AST is never freed.** Scope symbols are, in `pop_scope`, but the tree
  itself leaks at exit. Harmless for a one-shot compiler — valgrind reports no
  invalid accesses — but worth knowing before embedding the analyser in a loop.

## 10. Building and testing

```sh
make          # bison → flex → gcc
make run      # compile the pasta example
make test     # compile every example, check every exit status
make clean    # delete all generated files
```

The build order is forced by a real dependency, not convention: `bison -d`
generates `parser.tab.h`, which `lex.yy.c` includes for the token numbers, so
bison must run before flex. The makefile expresses this by making `lex.yy.c`
depend on `parser.tab.h`.

`run_tests.sh` compiles each example and compares the exit status against what
the file is supposed to do. Inside the test directories the expectation comes
from the filename — a name containing `fail` must be rejected, anything else must
compile — and the four top-level examples are listed explicitly because their
names carry no marker. The script exits non-zero if any case disagrees, so it is
usable as a CI gate.

To add a test: drop the file in `test_for_scope/` or `test_for_arithmetic/`, name
it `...pass.txt` or `...fail.txt`, and `make test` will pick it up with no edit
to the script.
